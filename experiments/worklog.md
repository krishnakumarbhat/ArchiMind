## Key Insights
- (setup) Baseline is linear RAG, not agentic: 3-node straight-edge graph, single-shot generation, no tools/validator/sandbox.
- (run 1) v0 on synthetic_bad_repo: harness_score=80.09 (validity 1.0, F1 0.68, dead 0.5, RAM 19.7MB). Regex edges already lose ~0.32 F1 vs AST truth — quantifies the CPG opportunity. Tiny-repo score is inflated; real repos (flask/requests) expected to drop F1 further and stress RAM.
- (run 1 caveat, discovered run 2) That 0.68 F1 is **not a quality signal**. v0's regex and the "ground truth" were the same blind technique on the same text; v0 has no caller/callee representation at all, so it was only ever scored in its own degenerate vocabulary.

Driver iterations should opportunistically re-probe `gemini-flash-latest`/3.8 and adopt if 200.
- (run 2) Potency re-ranking: **v1 (N2) has zero headroom** — v0 already scores `mermaid_validity_rate=1.0`, so reflection buys 0 of the 100 points and spends tokens. v2 (N3) was the only frontier node attacking the 50 points that are actually weak. N3 expanded; N2 left unexpanded with a recorded reason rather than quietly skipped.
- (run 2) A *second static parse is not an oracle*. Scoring an `ast`-based predictor against an `ast`-based truth returns 1.0 while both miss the identical edges. Any "CPG F1" number in this harness computed that way is unmeasurable by construction.
- (run 2) Dynamic oracle (`sys.settrace` + auto-harness) is the first independent ground truth here, and it immediately paid for itself by catching a real bug in my own CPG (eq. row 6: class-instantiation edges dispatched as `Cls.__init__`, not `Cls`) that no amount of static review had flagged.
- (run 2) One root cause explains every remaining weakness: **attribute-on-instance calls** (`self.s.query(uid)`). It caps `cpg_resolution_rate` at 0.5, `struct_recall_dyn` at 0.5, and drags `dead_code_acc` to 0.333. Fixing that one pattern is worth more than any remaining score-shaping.
- (run 2) Python 3.10 has no `code.co_qualname`, so a raw trace yields `fetch`, not `UserRepo.fetch`. Class identity has to be recovered from a code-object index built out of the repo's own modules, or the oracle and the CPG end up speaking different vocabularies and the comparison is meaningless.
- (run 2) `synthetic_bad_repo` has a **circular import** (repo→routes→repo) and cannot be imported at all, so it is unusable as a dynamic-oracle subject. Its `import routes` is also dead code — the fixture was hiding a finding. New acyclic `synthetic_cpg_repo` added; the old fixture is untouched so run-1 numbers stay comparable.

- (run 3) **A promotion that is provably precision-monotone on the trace it learned from is precision-DESTRUCTIVE on any independent trace.** Eq. row 8: the whole argument for edge promotion collapses if "observed" means "observed in the *training* trace". Measured: mode A holds precision 1.0 against its own fold and drops 0.6 -> 0.4286 against the held-out fold. This is the single most useful thing the loop learned, and it was only visible because the rule was *not* scored on the data it was fitted to.
- (run 3) Edge promotion (bind caller -> callee) and name promotion (bind bare callee name -> symbol) are not variants of one idea, they are different ideas with opposite behaviour. Edge promotion is **structurally incapable** of generalising: no rule is ever instantiated for a caller absent from the training fold, so held-out recall for unseen callers is 0 by construction (eq. row 9, confirmed empirically: 0.0). Name promotion transferred to callers that were never executed and moved unseen-caller recall 0.0 -> 0.2857.
- (run 3) The honest, decision-grade win: held-out recall **0.4286 -> 0.7143** at held-out precision **1.0** throughout, with the number of evaluation-confirmed edges rising 3 -> 5 and `cpg_resolution_rate` 0.4545 -> 0.6. Every promoted edge that the evaluation fold could check, it confirmed.
- (run 3) I found and fixed a bug in my own instrumentation mid-run: `split_caller_recall` was handed `promoted - cpg.call_edges`, which is always empty because promotion had already been applied. Every `recall_unseen_callers` was therefore pinned to 0.0 and mode B's generalisation was invisible until the subtraction was moved ahead of the apply. Caught only because the number was suspiciously round, not because a test failed.
- (run 3) A measured coverage ceiling beats a "needs more traces" hand-wave. A half-trace can only ever promote the half of unresolved call *names* it saw: ceiling **0.5** here (`commit`, `load` are fold-B-only). The deployment row, which sees all folds, promotes those two and drives the dead set down to exactly the one genuinely dead symbol — so the ceiling is the right thing to report, and it is a property of the trace budget, not of the rule.
- (run 3) **The standing metric misranks the better variant.** `harness_score` weights the structural term `30 * precision`, which is mathematically incapable of rewarding a recall gain, and charges every edge the evaluation fold could not re-exercise as a false positive. Result: mode B **loses** on the standing metric (66.23 vs 67.56) and **wins** on an F1 term (68.31 vs 64.56). The F1 number is reported alongside and deliberately *not* substituted -- swapping the metric mid-loop to make a variant look better is precisely the sin run 2 was convened to stop.
- (run 3) `dead_code_acc` is **not identified** under a held-out oracle: 0.0 strict for all three rows. Run 2 counted unexercised code as proven dead. The 20-point term needs to be gated behind the coverage bound before it can be believed at all.

- (run 4) **The 20-point `dead_code_acc` term was not "unidentified" — it was the constant 0, and it had a second hole that paid a do-nothing predictor in full.** `dead_symbols()` only emits symbols with in-degree 0, so `reverse(s) = {}` for every one of them, the `proven` bucket's guard `reverse(s) != {} AND ...` is `FALSE AND _`, and `proven` is empty for *every* graph and *every* predictor. Compounding it, the `if |dead| else 1.0` fallback pays a predictor that reports nothing dead a perfect 20/20. The term's range is exactly {0.0, 1.0}. Run 3 diagnosed this as an oracle-coverage problem; it is a contradiction in the definition (eq. row 13).
- (run 4) **I retracted my own run-3 proposal.** Run 3 said the standing metric misranked mode_b and proposed swapping `30*precision` for `30*F1`. The justification was "F1 is a lower bound against a partial oracle". That is false: `prec_D <= prec_T` holds but `rec_D <= rec_T` does **not** (D={1,2}, T={1,2,3,4,5}, P={1,2,6} gives rec_D=1.0 > rec_T=0.4), and F1 is monotone increasing in recall, so it inherits the sign-indefinite term. Precision stays precisely *because* it is the only well-posed direction. The retracted numbers are kept in the log under `harness_score_f1_RETRACTED` so the retraction is auditable.
- (run 4) **The repair is exactly score-neutral, and that is the proof.** The 20 dead points contributed **0.000** to every one of the three rows, so deleting them changes no score and only changes the ceiling from 100 to 80 (`score_unchanged_by_repair = True`, verified by subtraction `|v2def - v3| = 20*0.0`, not asserted). A term that can only ever contribute zero is 20 points of denominator inflation that made a binary flag look like a quality measurement.
- (run 4) **The fix is to stop asking the trace and ask the resolver.** A call site the resolver could not resolve is an *opaque* site, and the only thing it could have been is a call to a symbol whose bare name is the one recorded. So a predicted-dead symbol whose bare name matches an opaque name has an un-instrumented possible caller and is **un-adjudicable**; the rest are **certified**. Certified symbols have **zero false positives** under the resolver's own soundness — a strictly stronger claim than any partial trace supports, and it needs no execution at all. On `synthetic_promo_repo` it returns exactly `cache.Cache.stale`, the one genuinely dead symbol, and abstains on the two it cannot prove.
- (run 4) **The soundness argument has a checkable precondition, and real code breaks it.** A call whose callee has no extractable name (`factory()()`) is recorded as `<complex>`; its possible targets are un-nameable, so the name filter cannot see them and a live symbol could be certified wrongly. `soundness_precondition` therefore *checks* rather than assumes, and the term scores 0.0 when it fails. It **fails on 3 of 5 real repos** (flask, requests, rich) — the repair is sound on the synthetic fixtures and correctly refuses to score on real code. A fix that only works where you wrote the test is not a fix; the refusal is the deliverable there.
- (run 4) **The repaired term is 1.0 by construction, so it is a binary soundness verdict, not a graded signal.** Under the precondition every certified symbol is a true positive, so any accuracy-over-certification is identically 1.0. I report that limitation rather than dressing it up: the informative number is `certification_rate` (0.2 / 0.3333 / 0.3333), which is **deliberately unscored** because it rewards shrinking the dead set toward nothing. All three rows certify the *same single symbol*, so the repair changes what the 20 points **mean**, not which variant wins.
- (run 4) **The variant ranking is not identifiable, and that is the finding that outranks the repair.** `precision` 0.6/0.4286/0.5556 vs `precision_evaluable` **1.0/1.0/1.0**, with unadjudicable edges 2/4/4. The standing ranking (control 67.55 > mode_b 66.21 > mode_a 62.40) is produced *entirely* by edges the oracle never adjudicated. No aggregator fixes this — precision, F1, min(p,r) and Youden's J are all monotone in the same two contaminated ratios. The instrument now says `ranking_identifiable = False` instead of quietly producing a number.
- (run 4) **A name collision costs recall and never precision.** A live `a.Cache.load` and a dead `b.Cache.load` share a bare name, so the live one taints the dead one out of the certified set. Precision is preserved by construction; recall is not. This is the right direction to fail in for a gate that emits "safe to delete".
- (run 4) **Incidental find, out of scope for a metric node:** the old `dead_code_acc` reads **0.98-1.0** on flask/requests/rich — it would have looked *excellent* on real code — while the certification says 39-169 symbols with a failed precondition, and the predicted-dead set is polluted with **imported stdlib symbols** (`AssertionError`, `Path`, `string.hexlify`) because `load_repo_files` flattens tarballs by basename and `dead_symbols` never excludes non-local symbols. Queued as the next node; not fixed here, because fixing the pipeline while auditing the instrument is how you end up not knowing which change moved the number.

- (run 5) **Half of run 4's queued N7 premise was wrong, and re-probing it is what made the run worth anything.** The claim was "`dead_symbols()` includes imported stdlib symbols (`AssertionError`, `Path`, `string.hexlify`)". Re-probed: those names appear in **zero** predicted-dead sets on flask, requests, sqlmodel and rich. `dead_symbols()` iterates `self.symbols`, which is only ever populated with locally-defined modules, functions, classes and methods, so an imported symbol can never be a dead candidate. rich's `pathlib.Path` is a resolved call *target* -- a node in the graph, not a verdict. Retracted rather than quietly dropped.
- (run 5) **The basename defect was real and much bigger than logged.** `load_repo_files` keyed tarballs by `parts[-1]`, so distinct modules in different packages overwrite each other. sqlmodel: **131 of 171 analysis files destroyed** (171 files collapse to 40 unique basenames; `session` merged `sqlmodel.ext.asyncio.session` with `sqlmodel.orm.session`; `main` merged a `docs_src` tutorial with `sqlmodel.main`). flask 3 files, rich 2, requests 0. **Run 4's sqlmodel row was computed on a 40-file graph**, so every real-repo number in run 4 is retracted as a measurement of those repositories. The fixture numbers are unaffected (flat dirs, zero collisions), which is why parity held.
- (run 5) **Run 4's "zero false positives" was false, and its own precondition was the only thing hiding it.** The gate matched a dead symbol's bare name against the names of unresolved call sites. That misses (i) the **string-literal escape** -- `getattr(m,"s")` and `globals()["s"]` mention `s` only as a STRING -- and (ii) **scope** -- the opaque set is built from the analysis set, which skips `tests/`, so a test-only reference is invisible and `s` is certified anyway. Both are demonstrated on `synthetic_taint_repo`, the first fixture here with a *written-down* dead-code ground truth: the ungated filter certifies 4 symbols, **2 of them live**.
- (run 5) **The damning number is sqlmodel, not the synthetic fixture.** sqlmodel is the *one* real repo where run 4's `<complex>` precondition holds, so it is the one repo where run 4's gate actually fires -- and **107 of its 195 certified symbols are referenced outside the analysis set**. Demonstrated false positives, not counterfactual ones. flask 80/111, requests 43/84, rich 120/198 would have been the same. The global refusal was not a soundness mechanism; it was the only thing keeping a 55%-false-positive gate switched off, and the single repo where it switched on is exactly where the gate failed. This is the loop's second self-retraction (eq row 18, node N7b); run 4's formula is retained and still measured, only its soundness claim is withdrawn.
- (run 5) **The repair is an occurrence count, and it is structurally immune rather than better-tuned.** `certified = {s ∈ dead : occ[leaf(s)] == 1}` over the whole reference corpus, counting NAME tokens *and* identifier-shaped STRING tokens. Sound because every mechanism that can put a reference to `s` into a Python program names `s` somewhere in the source. There is no opaque-name set left to escape and no analysis scope left to fall outside of, so both holes are closed by construction rather than by another filter. The `<complex>` clause disappears entirely and the term stops refusing on real code: **4 / 22 / 22 / 27** certified on flask / requests / sqlmodel / rich, where run 4 certified **0 / 0 / 195 / 0**.
- (run 5) **Reported against interest: on raw count the replacement looks like a 9x regression on sqlmodel** (22 certified vs run 4's gated 195). It is not, because 107 of those 195 are demonstrated false positives -- 22 sound verdicts beats 88 unsound ones. The rule's genuine cost is conservatism: `certification_rate` is 2-20% on real repos. But `n_blocked_by_string_only` is 0-3 on every repo, so the blockers are `__all__` string entries and same-name collisions, not real callers. That is a *scope* artefact with the witnesses already sitting in the corpus, which is why it is queued as N9 instead of being claimed as a win.
- (run 5) **The third refusal in the harness's history fires on a fixture built to be broken.** `corpus_complete` requires every `.py` file in the artefact to have tokenised. It holds on 6 of 8 repos including all four real tarballs, and **refuses on `synthetic_bad_repo` and `synthetic_cpg_repo`** solely because each plants a `broken.py` that cannot tokenise. A repo with a syntax error has an *unknown* reference set, and the gate says so instead of certifying from a partial count.
- (run 5) **Three self-inflicted bugs, all caught by distrusting a round number.** (i) `04_symbol_domain.py`'s self-check fired on first execution and caught a bug in my own fixture -- I had written a symbol as unreferenced while another function called it. (ii) `run_n7` passed dotted keys to the dynamic oracle, which requires `.py` suffixes; the oracle silently observed **zero** modules and reported a precision of exactly `0.0` on every synthetic fixture. Same instinct that caught run 3's `split_caller_recall` bug -- a number that is too round is a bug until proven otherwise. Now guarded to `status: unvalidated`. (iii) `harness_score_v4` was briefly on the 100-point formula while declaring `max_metric: 80` (99.56/80); replaced with `GATE_MOD.gated_score` so the only thing that differs from run 4 is the pipeline, not the arithmetic.
- (run 5) Novelty **28/100 -> engineering track, no LaTeX paper.** Adversarial check scored it 25. The mechanism is a direct application of defensive / scope-sensitive soundness (Smaragdakis & Kastrinis, ECOOP 2018, 23 cites) to a Python CPG; gating dead-code verdicts with conservative call-graph information is prior art (Azad et al. USENIX Sec 2019, 132 cites; bundler tree-shaking assumes rather than refuses). The exact occurrence-count rule and the corpus-completeness precondition were **not found in any source** and are logged as UNVERIFIED-novel, not novel.
